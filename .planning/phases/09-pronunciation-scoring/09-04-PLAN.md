## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| student upload request -> server pipeline | Already-authenticated student upload triggers server-owned scoring; the score is computed server-side, never submitted by the client |
| server-role client -> pronunciation_scores | Only the server-role Supabase client writes scores (consistent with all other server-owned writes in this file) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-08 | Tampering | Client-submitted / forged pronunciation score | mitigate | Scoring runs entirely server-side inside `uploadAttemptAudioClip`; the client never sends a score and the route payload does not accept one; the server-role client performs the write under the 09-02 RLS `with check` ownership predicate. |
| T-09-09 | Denial of Service | A pronunciation-scoring failure blocking the student's core homework feedback | mitigate | Scoring is wrapped in a best-effort try/catch (warmTtsAudioCache pattern); on any failure the upload still returns `{ ok: true }` and the meaning/pattern feedback proceeds — scoring is strictly additive (RESEARCH.md Open Question 1). |
| T-09-10 | Information Disclosure | Reference text / audio content leaking into logs on scoring failure | mitigate | The `audio.pronunciation_scoring_failed` warn logs only structured ids + a fixed error code/message, never the audio bytes or reference sentence, matching the existing logging convention in this file. |
</threat_model>
