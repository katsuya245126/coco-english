# Phase 11.1: Coco Chat Opening Line & Dynamic-Turn Runnability - Context

**Gathered:** 2026-07-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 11.1 (urgent, inserted after Phase 11) makes zero/partial-authored-turn chat missions actually runnable end-to-end. Two confirmed gaps: (1) nothing generates Coco's opening line — every generator requires a prior `studentTranscript` (`conversationTurnInputSchema` min-1), so a zero-turn chat mission shows a blank chat screen; (2) `audio-upload.ts` hard-fails (`invalid_audio`) any uploaded turn whose `turnOrder` has no matching template in the immutable mission snapshot (~line 559) — since chat missions skip the exact-turn-count check (11-01), this rejects **all** turns of a zero-authored mission and every dynamic turn beyond the authored templates of a partial one. The snapshot turn also supplies the evaluator's `missionQuestion`/`targetExample` and the student hint ladder.

This phase must land before Phase 11's Wave 4 manual-review UAT (11-07), which cannot exercise chat missions end-to-end while this gap exists.

Out of scope: everything already owned by Phase 11's remaining plans (student scene-premise card and thinking indicator 11-04, teacher form controls 11-05, evidence-page chat additions 11-06, UAT 11-07), any change to preset-mission behavior, open-ended free chat, and mascot/visual work.

</domain>

<decisions>
## Implementation Decisions

### Opening-Line Source (advisor-researched; user picked recommended option)
- **D-01:** The opener is **generated at mission-save time into a teacher-editable field** on the mission form — the exact D-07 (Phase 11) generate-then-edit pattern already shipped for the scene premise (`generatePremiseAction`, commits 48900897/a2628ba9). A runtime per-attempt opener generator was explicitly rejected (latency, runtime moderation cost, unreviewed child-facing copy, and it wouldn't fix the snapshot gate).
- **D-02:** The saved opener is **stored as the turn-1 template row** in the mission (and therefore in the immutable assignment snapshot). Turn 1 then clears the `audio-upload.ts` snapshot gate with no changes to that gate, and `previousCocoLine` exists by construction for every dynamic turn N≥2.
- **D-03:** **Save-time validation backstop:** a chat mission must end up with an opener (generated or hand-typed) to save. This replaces "allow zero-turn saves with nothing to show" — the zero-turn save path shipped in 11-01/11-05 is superseded for the opener slot specifically.
- **D-04:** Same opener for every student on a mission is accepted (matches preset-mission precedent); per-student opener variety was considered and deferred.

### Opener Safety & Failure Posture
- **D-05:** The opener takes the **teacher-content path**: the teacher reviewed/edited it before saving, so **no runtime moderation** — it is trusted exactly like authored preset lines and the scene premise, and is **voiced through the normal (cacheable) TTS path**, not the dynamic-line path.
- **D-06:** Opener generation failure at save time = **retry-in-form**: the generate action shows a soft error; the teacher clicks generate again or types the opener by hand. The D-03 validation backstop is what actually gates saving — the generator itself never blocks or auto-fills canned copy. Mirrors `generatePremiseAction` failure behavior.

### Dynamic-Turn Snapshot Dependency (advisor-researched; user picked recommended option)
- **D-07:** **Chat-aware gate + honest nullable threading** — no fabricated data, no schema change:
  - The `snapshotTurn` gate in `audio-upload.ts` (~559) allows dynamic turns when `conversationMode === true` and the existing server cap check passes (reuse `canGenerateNextDynamicTurn` from `mission-flow.ts:114`; never exceed `HARD_TURN_CAP`).
  - The evaluator's `missionQuestion` for dynamic turn N = the **persisted `attempt_turns.coco_line` from turn N−1** (real data 11-03 already writes; the existing `previousCocoLine` lookup at ~925 must move earlier in the pipeline, before evaluation).
  - The evaluator accepts **`targetExample: string | null`**; grounding on dynamic turns comes from `targetPattern` + the real dynamic question. A synthesized/virtual snapshot turn was explicitly rejected — a fabricated example biases `improved_sentence` (the sentence students are forced to repeat, D-01 Phase 11) and the D-14 pattern badge.
  - **Skip the exact-match fast path** (~754) when `targetExample` is null (it could false-accept against nothing/canned text).
- **D-08:** **Pronunciation scoring needs no changes:** research confirmed originals score against the transcript itself (~730-732) and repeats against `improved_sentence` (guaranteed present whenever a repeat is required — `targetExample` fallback is effectively dead code for dynamic turns).
- **D-09:** Materializing per-attempt template rows (new columns) was rejected as duplicate work — `coco_line` persistence already exists from 11-03.

### Student Hints on Dynamic Turns
- **D-10:** Dynamic turns show **one generic pattern-derived hint** (e.g., "Try using: {target pattern / its example sentence}") instead of an authored hint ladder. Keeps the no-harsh-failure scaffold for struggling students without presenting synthetic hints as teacher-authored. `MissionFlowShell.tsx` consumes `turns[flow.turnIndex]` (~282) and `hintLadder` (~751), so the client needs a dynamic-turn step shape for turns beyond the snapshot templates.

### Claude's Discretion
- Exact opener-generator prompt/schema design (mirror `scene-premise-generator.ts`; input = scenePremise + targetPattern; classroom-safe Coco tone).
- Where the opener field lives in the form and how it writes into the turn-1 template row on save (including edit-path behavior for pre-existing zero-turn chat missions in the DB — forward-only handling acceptable, per Phase 11 D-08 precedent).
- Exact shape of the generic dynamic-turn hint and how the client detects a dynamic (non-snapshot) turn.
- How `targetExample: string | null` threads through evaluator prompt wording without regressing preset-mission evaluation (shared prompt — needs regression tests).
- Ordering details for moving the `previousCocoLine` lookup ahead of evaluation in the shipped audio-upload pipeline.

</decisions>

## Existing Code Insights

### Reusable Assets
- `scene-premise-generator.ts` + `generatePremiseAction`: the opener generator + form action are near-copies (same adapter pattern, same form UX).
- `attempt_turns.coco_line` persistence (11-03): already provides the real `missionQuestion` for every dynamic turn N≥2 — no new persistence needed.
- `canGenerateNextDynamicTurn` (mission-flow.ts): the server cap check the relaxed gate reuses.
- Phase 8 TTS path: opener is a stable authored line → normal cacheable TTS, unlike dynamic lines.

### Established Patterns
- Server-only AI adapters with injected fake clients; no paid API calls in tests.
- AI-06 boundary: mission-flow.ts stays persistence/gate-only; generation stays in audio-upload.ts / server actions.
- Additive-only schema changes; **this phase needs no migration** (opener reuses the turn-1 template slot; nullable threading is type-level).
- Reference-text integrity lesson (Phase 9 bug): never score/evaluate against fabricated or mismatched reference text — drove the rejection of virtual snapshot turns.

### Integration Points
- Mission form (teacher): opener field + generate action + D-03 save validation → turn-1 template row.
- `audio-upload.ts`: relaxed chat-aware gate, nullable `targetExample` threading, fast-path skip, `previousCocoLine` reorder.
- `turn-evaluator.ts` + prompt: accept null targetExample; regression-test preset missions.
- `MissionFlowShell.tsx`: dynamic-turn step beyond snapshot turns + generic pattern hint (coordinates with in-flight 11-04 UI work).

</code_context>

<specifics>
## Specific Ideas

- The two locked decisions compose deliberately: opener-as-turn-1-template means every dynamic turn has a real previous coco_line, so the nullable threading never sees a missing question.
- The opener is the one Coco line where authoring-time human review is possible — so it gets the trusted teacher-content treatment; all other dynamic lines keep the Phase 11 runtime moderation pipeline unchanged.

</specifics>

<deferred>
## Deferred Ideas

- Per-student/per-attempt opener variety via a runtime transcript-optional generator — revisit post-pilot if fixed openers feel stale; `attempt_turns.coco_line` persistence works either way, no schema conflict.
- Richer dynamic-turn hint generation (LLM-derived contextual hints per turn) — beyond the generic pattern hint; would need its own moderation/cost discussion.

</deferred>
