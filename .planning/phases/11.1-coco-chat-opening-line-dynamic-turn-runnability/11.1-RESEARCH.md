### Locked Decisions

**Opening-Line Source (advisor-researched; user picked recommended option)**
- **D-01:** The opener is generated at mission-save time into a teacher-editable field on the mission form — the exact D-07 (Phase 11) generate-then-edit pattern already shipped for the scene premise (`generatePremiseAction`, commits 48900897/a2628ba9). A runtime per-attempt opener generator was explicitly rejected (latency, runtime moderation cost, unreviewed child-facing copy, and it wouldn't fix the snapshot gate).
- **D-02:** The saved opener is stored as the turn-1 template row in the mission (and therefore in the immutable assignment snapshot). Turn 1 then clears the `audio-upload.ts` snapshot gate with no changes to that gate, and `previousCocoLine` exists by construction for every dynamic turn N≥2.
- **D-03:** Save-time validation backstop: a chat mission must end up with an opener (generated or hand-typed) to save. This replaces "allow zero-turn saves with nothing to show" — the zero-turn save path shipped in 11-01/11-05 is superseded for the opener slot specifically.
- **D-04:** Same opener for every student on a mission is accepted (matches preset-mission precedent); per-student opener variety was considered and deferred.

**Opener Safety & Failure Posture**
- **D-05:** The opener takes the teacher-content path: the teacher reviewed/edited it before saving, so no runtime moderation — it is trusted exactly like authored preset lines and the scene premise, and is voiced through the normal (cacheable) TTS path, not the dynamic-line path.
- **D-06:** Opener generation failure at save time = retry-in-form: the generate action shows a soft error; the teacher clicks generate again or types the opener by hand. The D-03 validation backstop is what actually gates saving — the generator itself never blocks or auto-fills canned copy. Mirrors `generatePremiseAction` failure behavior.

**Dynamic-Turn Snapshot Dependency (advisor-researched; user picked recommended option)**
- **D-07:** Chat-aware gate + honest nullable threading — no fabricated data, no schema change:
  - The `snapshotTurn` gate in `audio-upload.ts` (~559) allows dynamic turns when `conversationMode === true` and the existing server cap check passes (reuse `canGenerateNextDynamicTurn` from `mission-flow.ts:114`; never exceed `HARD_TURN_CAP`).
  - The evaluator's `missionQuestion` for dynamic turn N = the persisted `attempt_turns.coco_line` from turn N−1 (real data 11-03 already writes; the existing `previousCocoLine` lookup at ~925 must move earlier in the pipeline, before evaluation).
  - The evaluator accepts `targetExample: string | null`; grounding on dynamic turns comes from `targetPattern` + the real dynamic question. A synthesized/virtual snapshot turn was explicitly rejected — a fabricated example biases `improved_sentence` (the sentence students are forced to repeat, D-01 Phase 11) and the D-14 pattern badge.
  - Skip the exact-match fast path (~754) when `targetExample` is null (it could false-accept against nothing/canned text).
- **D-08:** Pronunciation scoring needs no changes: research confirmed originals score against the transcript itself (~730-732) and repeats against `improved_sentence` (guaranteed present whenever a repeat is required — `targetExample` fallback is effectively dead code for dynamic turns).
- **D-09:** Materializing per-attempt template rows (new columns) was rejected as duplicate work — `coco_line` persistence already exists from 11-03.

**Student Hints on Dynamic Turns**
- **D-10:** Dynamic turns show one generic pattern-derived hint (e.g., "Try using: {target pattern / its example sentence}") instead of an authored hint ladder. Keeps the no-harsh-failure scaffold for struggling students without presenting synthetic hints as teacher-authored. `MissionFlowShell.tsx` consumes `turns[flow.turnIndex]` (~282) and `hintLadder` (~751), so the client needs a dynamic-turn step shape for turns beyond the snapshot templates.

## Summary

This phase closes two verified, code-confirmed gaps that make chat-mode missions (Phase 11, CHAT-01..06) non-functional whenever a teacher saves a mission with zero or partial authored turns — which the Phase 11 form (`MissionForm.tsx`, already committed) explicitly allows and even encourages ("Turns (optional preview)... Coco generates turns live"). Both gaps were independently confirmed by reading the live code, not assumed from the CONTEXT.md description.

**Gap 1 (opening line):** `missionFormSchema`/`toTurnRows` in `mission-service.ts` permit `turns: []` when `conversationMode === true`, and nothing in the codebase generates a first Coco line — `conversationTurnInputSchema.studentTranscript` requires a non-empty student transcript, which cannot exist before the student has spoken. Result: a zero-turn chat mission produces a blank first screen (`MissionFlowShell.tsx` line 746 only renders `StepBuddyQuestion` when `currentTurn` is truthy, and `currentTurn = turns[flow.turnIndex]` is `undefined` when `turns.length === 0`).

**Gap 2 (snapshot gate):** `audio-upload.ts` line 559 does `snapshot?.turns.find((t) => t.turnOrder === input.turnOrder)` and hard-fails `invalid_audio` if no match exists — with no `conversationMode` branch at all. Since chat missions already skip the turn-count-match refine (11-01), a chat mission's snapshot may have 0-1 turns while `HARD_TURN_CAP` allows up to 8 dynamic turns; every turn beyond the authored templates is rejected outright, including via an existing regression test (`tests/server/audio-upload.test.ts:887`, "rejects turn orders outside the mission snapshot") that will need a conversation-mode-aware counterpart.

**Primary recommendation:** Implement D-01/D-02 by adding an opener-generator adapter that is a near-literal copy of `scene-premise-generator.ts` (same deps/client/resolveApiKey/createClient/typed-result-union shape), wired through a new `generateOpenerAction` mirroring `generatePremiseAction`, writing the accepted/edited text into `turns[0]` (prompt field, or a new dedicated field — Claude's discretion) before `createMissionAction`/`updateMissionAction` submit. Implement D-07 by adding a `conversationMode` branch to the `audio-upload.ts` snapshot-gate check (allow when `canGenerateNextDynamicTurn(turnOrder)` is true even with no matching snapshot turn), moving the `previousCocoLine` lookup (currently at ~925, after the turn write) to before evaluation for dynamic turns, and threading `targetExample: string | null` through `EvaluateOriginalTurnInput`/`buildOriginalPrompt`/`isExactTargetMatch` call sites. Implement D-10 in `MissionFlowShell.tsx` by detecting `!currentTurn && conversationMode` and rendering a dynamic-turn variant of `StepBuddyQuestion` with a single generic hint instead of `hintLadder`.

### Pattern 1: Generate-then-edit teacher content (D-01, extending D-07 Phase 11)
**What:** A server action calls an AI adapter to produce a draft string; the draft is shown in an editable form field; the teacher may regenerate, hand-edit, or accept as-is; only the save action persists the final value. No runtime AI call ever touches this text again.
**When to use:** Any teacher-facing content that must be reviewed once before it becomes classroom-safe "trusted" content (already applied to `scenePremise` in 11-05).
**Example:**
```typescript
// Source: src/app/teacher/missions/actions.ts (existing generatePremiseAction,
// the exact pattern to mirror for generateOpenerAction)
export async function generatePremiseAction(
  input: unknown,
): Promise<GeneratePremiseActionResult> {
  await requireTeacherProfile();
  const parsed = scenePremiseInputSchema.safeParse(input);
  if (!parsed.success) {
    return { ok: false, error: parsed.error.issues[0]?.message ?? GENERATE_PREMISE_FAILURE };
  }
  const result = await generateScenePremise(parsed.data);
  if (!result.ok) {
    return { ok: false, error: GENERATE_PREMISE_FAILURE };
  }
  return { ok: true, scenePremise: result.scenePremise };
}
```

**When to use:** Any new server-only OpenAI-calling adapter (the opener generator).

**What:** Instead of a hard `if (!snapshot || !snapshotTurn) return invalid_audio`, branch on `conversationMode` to allow a `turnOrder` with no matching template, as long as the server-owned hard cap still permits it.
**When to use:** The exact `audio-upload.ts` ~558-565 gate this phase must change.
**Example (illustrative, not literal code to copy — the real implementation is Claude's discretion within D-07's constraints):**

### Anti-Patterns to Avoid
- **Synthesizing a virtual/fake snapshot turn for dynamic turns:** Explicitly rejected by D-07. A fabricated `targetExample` would bias `improved_sentence` (the sentence students are forced to repeat) and the pattern badge (D-14, Phase 11). Thread `null` honestly instead.
- **Running the opener through runtime moderation:** Explicitly rejected by D-05. The opener is teacher-reviewed content and should use the same trust level as preset authored lines and the scene premise — routing it through `isContentSafe` would be inconsistent with that trust model and add unnecessary latency/cost.
- **Voicing the opener through the dynamic-line TTS path:** D-05 requires the opener use the normal cacheable TTS path (same as other snapshot-turn prompts), not the newer dynamic-coco-line path used for turns N≥2.
- **Adding new columns/tables for per-attempt template materialization:** Rejected by D-09 — `attempt_turns.coco_line` (migration `202607030001`, already live) is sufficient; do not duplicate this data.
- **Auto-filling canned copy when opener generation fails:** Rejected by D-06 — the generator must never silently substitute a canned line; only the teacher's own retry or hand-typed text can fill the opener slot. This mirrors `generatePremiseAction`, which also never auto-fills on failure.
- **Reordering `previousCocoLine` lookup without re-verifying it happens strictly before the evaluation call:** The existing code (line ~925) computes it AFTER the turn write. Moving it earlier changes control flow inside a fairly dense function (`uploadAttemptAudioClip`); regression tests must assert the lookup happens before `evaluateOriginalTurn`/`isExactTargetMatch` are invoked for a dynamic turn.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Server-side hard cap enforcement for dynamic turns | A second cap-check inline in `audio-upload.ts` | `canGenerateNextDynamicTurn` (`mission-flow.ts:114`), imported and reused as-is | Already exists, already tested, already the single source of truth for `HARD_TURN_CAP`; duplicating the check risks drift between two cap definitions |

**Key insight:** This phase is deliberately scoped to avoid any new schema, any new table, and any new generation pipeline duplication — every piece of data the fix needs (`coco_line`, `canGenerateNextDynamicTurn`, `conversationMode`, `targetPattern`) already exists and was written by Phase 11. The work is entirely about *relaxing an over-strict gate* and *filling one missing generator*, not building new infrastructure.

## Common Pitfalls

### Pitfall 1: Forgetting the client-side dynamic-turn detection breaks silently
**What goes wrong:** If Gap 2 (server gate) is fixed but Gap 1 or the `MissionFlowShell.tsx` dynamic-turn UI branch is missed, the server will happily accept and process dynamic turns, but the student will see a blank step card (no `StepBuddyQuestion` renders) because `currentTurn` stays `undefined` for `turnIndex >= 1`.
**Why it happens:** `currentTurn = turns[flow.turnIndex]` (line 282) and the render guard `flow.step === "question" && currentTurn` (line 746) both require a defined snapshot turn; the server fix alone does not add a client rendering path for turns beyond `turns.length`.
**How to avoid:** Both gaps must land together (or the client fix must land first/atomically) — do not ship the server relaxation without the corresponding `MissionFlowShell.tsx` dynamic-turn step (D-10).
**Warning signs:** Manual test of a chat mission plays turn 1 (the opener) fine, then goes blank/stuck on turn 2.

### Pitfall 2: Regressing preset-mission evaluation when making `targetExample` nullable
**What goes wrong:** `EvaluateOriginalTurnInput.targetExample` is currently required (`string`, not optional) and is used directly in `buildOriginalPrompt` and `validOriginalInput` (`turn-evaluator.ts` lines 49-142). Widening the type to `string | null` without auditing every call site and prompt-construction branch could make `validOriginalInput` silently reject preset-mission calls (which still always have a real `targetExample`) or send `"null"` (stringified) into the prompt.
**Why it happens:** The type/schema and the prompt-builder are two separate places that both assume non-null; a partial edit fixes one but not the other.
**How to avoid:** Add explicit regression tests asserting: (a) preset-mission calls with a real `targetExample` behave identically to today (same prompt shape, same fast-path behavior); (b) dynamic-turn calls with `targetExample: null` skip the fast path (D-07) and produce a sensible prompt that doesn't literally interpolate the word "null".
**Warning signs:** Existing preset-mission tests in `tests/server/audio-upload.test.ts` (e.g. "uses semantic evaluation for a relevant open-ended answer," line ~361) start failing after the nullable threading change.

### Pitfall 3: The existing "rejects turn orders outside the mission snapshot" test will need updating, not just passing
**What goes wrong:** `tests/server/audio-upload.test.ts:887` currently asserts `turnOrder: 999` on ANY mission returns `invalid_audio`. After D-07's chat-aware gate, this must remain true for **preset** missions (verify the test's fixture is non-chat) but a **new** test must assert the opposite for chat missions within the hard cap (turnOrder ≤ 8, no matching template, `conversationMode: true` → NOT rejected).
**Why it happens:** A single existing test currently encodes the old universal behavior; the planner must explicitly add a counterpart rather than assume the old test alone provides coverage.
**How to avoid:** Plan a task that (a) confirms the existing test's fixture is a preset (non-chat) mission and still passes unchanged, (b) adds a new test for a chat-mode mission where `turnOrder` exceeds `snapshot.turns.length` but is ≤ `HARD_TURN_CAP`, expecting success, and (c) adds a test for `turnOrder > HARD_TURN_CAP` on a chat mission still being rejected (cap still enforced).
**Warning signs:** Only one of the two behaviors gets test coverage, leaving a silent regression risk for whichever mission type wasn't retested.

### Pitfall 4: D-03's save-time validation backstop needs a precise definition of "has an opener"
**What goes wrong:** If the validation only checks `turns.length >= 1` (matching the existing non-chat refine at `missionFormSchema` line 75-78: `value.conversationMode || value.turns.length >= 1`), a chat mission could technically pass with an empty-string `prompt` on turn 1 if the form ever constructs a placeholder turn object without content.
**Why it happens:** The current schema's chat-mode branch skips both the turn-count-match refine AND the turns.length >= 1 refine entirely (`value.conversationMode || ...` short-circuits both refines to true when `conversationMode` is true) — meaning chat missions currently have NO structural requirement on `turns` content at all. D-03 must add a new, chat-specific refine, not just remove the old bypass.
**How to avoid:** Add an explicit new `.refine()` in `missionFormSchema` (and mirror in `missionSnapshotSchema` if the invariant should hold at snapshot-assembly time too) requiring: `!conversationMode || (turns.length >= 1 && turns[0].prompt.trim().length > 0)`. Confirm `missionTurnInputSchema.prompt` already has `.min(1, ...)` (it does — line 25) — so once a turn-1 object exists with a real string, the existing per-turn schema already enforces non-empty; the gap is only that chat mode currently allows `turns` to be `[]` entirely, bypassing the per-turn schema altogether.
**Warning signs:** A chat mission saves successfully with zero turns despite the "backstop," because the refine addition was skipped or scoped incorrectly.

### Pitfall 5: `previousCocoLine` reorder must not break the moderation ordering invariant
**What goes wrong:** `runConversationTurn`'s comment explicitly documents a strict, never-reordered pipeline: (a) hard-cap check, (b) moderate student input FIRST, (c) generate, (d) moderate output, (e) shared fallback, (f) persist. The `previousCocoLine` lookup currently happens just before this pipeline is invoked (line ~925-936), which is ALREADY before `runConversationTurn` runs. The needed reorder is to move it earlier still — before the *evaluation* call (`evaluateOriginalTurn`, which happens earlier in the function, around line 774-784) — not to touch the `runConversationTurn` internal ordering at all.
**Why it happens:** Two different "previous line" needs exist in the same function: the evaluator needs it as `missionQuestion` (new, this phase), and `runConversationTurn` already needs it as grounding context (existing, Phase 11). Conflating these two reads or accidentally duplicating/removing one is an easy mistake in a ~1100-line file.
**How to avoid:** Introduce the lookup once, early (before `evaluateOriginalTurn`), and pass the SAME resolved value both to the evaluator call (as `missionQuestion` for dynamic turns) and to `runConversationTurn`'s `context.previousCocoLine` (replacing the current in-place lookup at ~925). Do not add a second independent query.
**Warning signs:** Two separate `.select("coco_line")` queries against `attempt_turns` for the same turn in the same request; or `runConversationTurn` receiving a `previousCocoLine` that differs from what was used as `missionQuestion`.

## Open Questions (RESOLVED)

1. **RESOLVED — Does the D-03 save-time backstop apply to `missionSnapshotSchema` as well as `missionFormSchema`?**
   - What we know: `missionFormSchema` (form validation) and `missionSnapshotSchema` (assignment-time snapshot validation) currently have parallel, near-identical refines (both skip turn-count-match and turns.length>=1 when `conversationMode` is true).
   - Decision point considered: If a chat mission reaches assignment time with an empty `turns` array (for example, a pre-existing zero-turn mission), assignment must reject it rather than relying only on form validation.
   - Resolution: Mirror D-03 into `missionSnapshotSchema` as well as `missionFormSchema`. This defense-in-depth backstop prevents assignment of a pre-existing zero-turn chat mission.

2. **RESOLVED — Should the opener's `targetExample` and `hintLadder` (required by `missionTurnInputSchema`) be auto-derived, or does the teacher also fill them for turn 1?**
   - What we know: `missionTurnInputSchema` requires `prompt`, `targetExample`, and a full `hintLadder` (3 tiers) for every turn, including whatever becomes turn 1 for a chat mission.
   - Decision point considered: CONTEXT.md's D-01/D-02 focus on the opener line while the existing turn contract also requires `targetExample` and `hintLadder`; those required fields need honest values without adding teacher form burden or a schema fork.
   - Resolution: Serialize a complete existing `MissionTurnInput` without a chat-specific schema. Use the real target pattern as `targetExample`, and derive all three transparent hint tiers from that same pattern/frame; do not invent a student answer or label generated material as teacher-authored.

3. **RESOLVED — Does the client need a distinct visual/audio treatment for the opener turn vs. Coco's later dynamic lines?**
   - What we know: D-05 requires the opener use the normal cacheable TTS path (same as other prompt turns), which is already what happens automatically once it's `turns[0]` in the snapshot (no client change needed for turn 1 specifically — the existing `StepBuddyQuestion`/`CocoSpeechAudio` path already handles snapshot-turn prompts).
   - Decision point considered: Whether turn 1 in chat mode should differ from a normal preset first turn or remain the existing recording-required question/reply step.
   - Resolution: Keep turn 1 as the normal snapshot question/student-reply interaction, including ordinary `mission_prompt` TTS. The distinct dynamic client branch begins only when the current flow index has no authored snapshot turn.
