# Phase 10.1: Assignment Operations & Student History - Pattern Map

**Mapped:** 2026-07-12
**Inputs:** `10.1-CONTEXT.md`, `10.1-RESEARCH.md`, current repository

## Data Flow

```text
Teacher auth cookie -> requireTeacherProfile()
  -> assignment-operations service (service role + explicit teacher ownership joins)
  -> queue/activity/incomplete DTOs
  -> shared /teacher layout + route-specific server pages
  -> queue-snapshot route -> 30s client poll -> count/banner/notice

Student unlock cookie -> readStudentUnlock()
  -> assignment list/history service (service role + explicit student_id filter)
  -> Current/Past DTOs or final-attempt recap DTO
  -> student home / recap route
  -> on-demand signed audio action (cookie student scope repeated)
```

## Existing Code Excerpts to Mirror

### Teacher-owned nested read

From `src/server/teacher/audio-evidence.ts`:

```ts
const attempt = await supabase
  .from("attempts")
  .select(`... assignments!inner(... classes!inner(id, teacher_id)) ...`)
  .eq("id", input.attemptId)
  .eq("assignment_students.assignments.classes.teacher_id", input.teacherId)
  .maybeSingle();
```

Every service-role Phase 10.1 teacher read/write needs the same ownership-chain constraint. The current `overrideAssignmentStatusAction()` loads by assignment-student ID without a teacher filter; Phase 10.1 should route new actions through the stricter owned service and avoid copying that weakness.

### Student-scoped service read

From `src/server/student-access/assignment-list.ts`:

```ts
const { data, error } = await supabase
  .from("assignment_students")
  .select(`id, status, assignments!inner (...)`)
  .eq("student_id", studentId)
  .order("created_at", { ascending: false });
```

The recap loader must start from the assignment-student row and apply both `.eq("id", assignmentStudentId)` and `.eq("student_id", studentId)` before following the latest attempt.

### Defensive snapshot parse

From `src/server/student-access/assignment-list.ts`:

```ts
const parsed = missionSnapshotSchema.safeParse(assignment.mission_snapshot);
if (!parsed.success) continue;
```

Use the same schema for recap prompt reconstruction. A malformed snapshot should return not found/unavailable for that recap rather than crash the entire student home.

### Server-owned status transition

From `src/app/teacher/evidence/[attemptId]/actions.ts`:

```ts
assertTransitionRequest({
  previousStatus,
  nextStatus: input.nextStatus,
  actorType: "teacher",
  actorId: profile.id,
  reasonCode: "teacher_override",
  occurredAt: nowIso,
});
```

Request retry must retain transition validation and `assignment_status_events`. Mark reviewed/reopen are receipt mutations and must not call this status transition helper.

### Atomic final-attempt pointer

From `supabase/migrations/202607100001_complete_student_attempt_rpc.sql`:

```sql
update public.assignment_students
set status = 'completed',
    submitted_at = v_now,
    latest_attempt_id = p_attempt_id
where id = p_assignment_student_id;

update public.attempts
set status = 'completed', completed_at = v_now
where id = p_attempt_id;
```

Past recaps should trust this pointer and timestamp instead of scanning for a “best” attempt.

## Landmines

- Do not make `submission_review_receipts` the completion source of truth.
- Do not clear `latest_attempt_id` merely to mark reviewed; only the existing retry transition may reopen student work.
- Do not place external notification settings in the UI; D-06 is in-app only.
- Do not auto-refresh the visible inbox on a poll result.
- Do not include completed items in Current or missed items in Past; D-22 supersedes the wording in an early brainstorm option.
- Do not expose teacher evidence actions or teacher-owned URLs to the student recap.
- Do not put permanent “Move back to Needs review” as a bottom detail-page button.
