## Summary

The existing model already owns the hard parts that must not be duplicated: `assignment_students` stores the current student homework status and `latest_attempt_id`; `attempts.completed_at` plus `assignment_students.submitted_at` establish completion order; `assignment_status_events` audits status changes; mission snapshots preserve Coco prompts; attempt turns hold transcripts/evaluation; audio clips carry retention metadata; pronunciation scores are keyed to clips. Phase 10.1 should add a thin teacher-workflow layer and new query/presentation services over these sources.

The recommended additive data model is:

1. `classes.review_policy` with allowed values `every_submission` and `flagged_only`, defaulting to `every_submission`.
2. `submission_review_receipts`, keyed uniquely by `(teacher_id, attempt_id)`, containing `first_viewed_at`, `reviewed_at`, and timestamps. It records workflow state without changing `assignment_students.status`. Clearing `reviewed_at` reopens the current review task while preserving the original first-view receipt; `updated_at` records the latest workflow mutation. Ownership is verified through attempt → assignment_student → assignment → class → teacher before every service-role write.

Needs-review eligibility stays derived instead of materializing a second queue: the latest attempt is flagged when `attempts.needs_review_reason` is non-null; a row is pending when it is flagged or its class policy is `every_submission`, and its receipt has no `reviewed_at`. A `flagged_only` class still exposes ordinary completions in All activity. `needs_review_reason` must remain populated after teacher acceptance so reopening a formerly flagged submission returns it to Needs review even under flagged-only policy. This keeps class policy authoritative, avoids completion-path fan-out, and preserves the existing atomic completion RPC.

For 30-second freshness, add one authenticated, no-store queue-snapshot endpoint consumed by a client component in `src/app/teacher/layout.tsx`. The shared layout owns sidebar counts and off-page notices. On `/teacher`, a changed snapshot shows “new submissions” without refreshing the server-rendered row list; clicking the banner calls `router.refresh()`. This meets D-12–D-15 without Supabase Realtime or a general notification platform.

Student history should extend `listStudentAssignments()` into a paginated, student-scoped home loader and add a separate recap loader. The recap must authorize from the unlock cookie's `studentId`, require the requested `assignment_students` row to be `completed`, and follow only `latest_attempt_id`. It can reuse the evidence-mapping concepts in `src/server/teacher/audio-evidence.ts` but should not reuse the teacher authorization function itself.

No new npm packages are required.

## Existing Patterns to Reuse

- `requireTeacherProfile()` and ownership-filtered service-role reads in `src/server/teacher/audio-evidence.ts` establish the teacher authorization pattern.
- `overrideAssignmentStatusAction()` already validates server-owned transitions and appends `assignment_status_events`; Request retry should continue through that transition boundary rather than create review-specific status logic.
- `getAttemptEvidenceForTeacher()` already maps mission snapshot questions, transcripts, evaluation, audio clips, and pronunciation evidence. Extract only genuinely shared pure mapping helpers if useful; keep teacher and student authorization entry points separate.
- `listStudentAssignments()` already scopes by unlock-cookie student ID, filters canceled assignments, parses snapshots defensively, and applies late-at-read-time semantics.
- `complete_student_attempt()` atomically writes `submitted_at`, `latest_attempt_id`, completed statuses, and the status event. Do not modify it merely to populate the teacher queue; derive eligibility from the completed row and class policy.
- `bucketAssignmentStudents()` remains the per-assignment drill-down contract. Cross-class queues need new types/helpers instead of widening this pure assignment-scoped function.
- Existing tests commonly separate pure domain tests, mocked Supabase server tests, schema-source assertions, and env-gated Playwright flows.

## Recommended Data Model

### `classes.review_policy`

- Prefer a Postgres enum `class_review_policy` with `every_submission` and `flagged_only` or a text column with an explicit check constraint; the existing schema uses enums for bounded workflow vocabulary, so an enum is consistent.
- `NOT NULL DEFAULT 'every_submission'` preserves D-05 for all existing classes.
- Authenticated teacher updates remain constrained by existing class ownership RLS.

### `submission_review_receipts`

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `teacher_id uuid not null references teacher_profiles(id) on delete cascade`
- `attempt_id uuid not null references attempts(id) on delete cascade`
- `first_viewed_at timestamptz`
- `reviewed_at timestamptz`
- `created_at` / `updated_at` timestamps
- `unique (teacher_id, attempt_id)`

The server should use an upsert for first view that never overwrites a non-null `first_viewed_at`, set `reviewed_at = now()` for Mark reviewed, and set `reviewed_at = null` for Undo/reopen. The row is a receipt/task state, not the source of student completion truth.

### Query invariants

- Always join attempts through `assignment_students.latest_attempt_id`; older attempts never become current queue rows.
- Derive flagged origin from non-null `attempts.needs_review_reason`, not the current assignment/attempt status. Teacher acceptance changes both statuses to completed but retains the reason for durable flagged-only reopen semantics.
- Use `assignment_students.submitted_at` for ordinary received time. For an AI-routed `teacher_review` row that has no submitted timestamp, use the matching `assignment_status_events.created_at` transition time as the immutable received time; do not use a later review mutation timestamp.
- Every service-role query/write must constrain `classes.teacher_id` to the authenticated teacher.
- Exclude canceled assignments from current queues and student lists. All activity may retain historical completed submissions only when the assignment was not hidden from the student at completion; do not invent canceled-history behavior beyond D-22.
- Stable queue ordering: `submitted_at DESC`, then `assignment_students.id DESC` as a deterministic tie-breaker.
- Stable Past ordering: `attempts.completed_at DESC`, then `assignment_students.id DESC`, five rows per page.

## Freshness Architecture

```text
Teacher server page renders queue rows + baseline snapshot
                 |
                 v
TeacherWorkspaceClient in /teacher/layout polls every 30s
                 |
                 +--> GET /api/teacher/queue-snapshot (auth, no-store)
                         returns count, unreadCount, newest pending item metadata
                 |
                 +--> sidebar count updates on every teacher route
                 +--> on /teacher: show “new submissions” banner; do not mutate rows
                 +--> elsewhere: show non-blocking notice with View link
                 |
                 +--> banner click -> router.refresh() -> new baseline and rows
```

Guardrails:

- Poll immediately on window focus/visibility return and otherwise at 30 seconds; stop the interval while hidden.
- Treat failures as non-blocking and retain the last known count.
- Compare a stable snapshot version (newest attempt ID/submitted timestamp plus count), not wall-clock time from the browser.
- Never auto-refresh `/teacher` when the version changes; that would violate D-13 by shifting rows during reading.

## Student History Data Flow

```text
readStudentUnlock() -> studentId
        |
        +--> listStudentAssignmentPages(studentId, tab, page)
        |      current: retry -> due soon -> later/no due; review stays current
        |      past: completed only; completed_at desc; limit 5 + total pages
        |
        +--> getCompletedMissionRecap(studentId, assignmentStudentId)
               require assignment_students.student_id == studentId
               require status == completed
               follow latest_attempt_id only
               parse assignment mission_snapshot for Coco prompts
               load attempt_turns + audio_clips + pronunciation_scores
               map expired/deleted audio to “Recording expired”
               signed audio URL requested separately on demand
```

The recap route must not accept a student ID, attempt ID, or audio owner from the browser as authority. The unlock cookie supplies the identity; requested IDs are resource selectors only.

## Common Pitfalls

### Pitfall 1: Treating “viewed” as “reviewed”

Opening evidence sets `first_viewed_at` and removes unread styling only. It must not set `reviewed_at`, remove the queue item, or mutate `assignment_students.status`.

### Pitfall 2: Reusing assignment status for review workflow

`completed` is the student's durable homework result. Reopening a teacher review task by changing it to `teacher_review` would break Past mission eligibility and violate D-11. Use the receipt layer.

### Pitfall 3: Polling with unconditional `router.refresh()`

This makes the visible inbox jump when new submissions arrive. Poll a lightweight snapshot and refresh only after the teacher clicks the banner.

### Pitfall 4: Leaking history through service-role reads

Student routes use a service client, so every recap/audio query must include the unlock-cookie `studentId` through the ownership chain. A guessed `assignmentStudentId`, `attemptId`, or `audioClipId` must return not found/unavailable.

### Pitfall 5: Showing an earlier attempt after retry

Past history must follow `assignment_students.latest_attempt_id` and require that attempt to be completed. Never list all attempts for the assignment student.

### Pitfall 6: Assuming audio presence from a row alone

Audio can be expired, purged, failed, or missing an object key. Map playback availability from `processing_status`, `object_key`, `deleted_at`, and `audio_expires_at`; preserve transcript and feedback regardless.

### Pitfall 7: One giant teacher page

Keep data loading in server services, queue presentation in reusable components, freshness in one layout client, and actions thin. This phase is broad enough that a single monolithic page would be hard to verify and would duplicate class/global behavior.

## Security Domain

### Applicable risks

- **BOLA / cross-tenant reads:** teacher IDs must scope every cross-class query; class/assignment/attempt IDs are not authorization.
- **Student history enumeration:** unlock-cookie student scope must be present in recap and audio lookup chains.
- **Service-role mutation abuse:** mark viewed/reviewed/reopen and policy actions must re-check authenticated ownership server-side.
- **CSRF/action misuse:** use Next server actions or same-origin authenticated route handlers; never expose service-role credentials or accept teacher identity in request bodies.
- **Signed URL leakage:** generate short-lived URLs on demand, not in initial history HTML or queue snapshots.
- **Sensitive notification payloads:** in-app notices should contain only student display name, assignment title, class name, and an owned View URL; no transcript/audio data.

### Threat-model expectation

Security enforcement is active at ASVS L1 and blocks high-severity threats. Every PLAN.md must include a `<threat_model>` block covering ownership, service-role boundaries, signed URLs, and cross-student/cross-teacher negative tests where relevant.

## Assumptions Log

- **[ASSUMED] Policy changes are live:** switching to `flagged_only` immediately removes ordinary unreviewed completions from Needs review; switching back may reveal still-unreviewed ordinary completions. This follows a derived queue and avoids silently marking work reviewed. If product intent differs, lock policy-at-submission semantics before implementation.
- **[ASSUMED] One teacher owns each class:** current schema has a single `classes.teacher_id`; receipts still store `teacher_id` to make ownership explicit and future-safe without introducing co-teachers.
- **[ASSUMED] All activity is bounded/paginated:** the exact page size is discretionary; use a small stable server-side page (for example 25) rather than an unbounded cross-class query.
- **[VERIFIED] Past completion timestamp:** the atomic completion RPC writes both `assignment_students.submitted_at` and `attempts.completed_at`; either is available, but Past should use the final attempt's `completed_at`.
- **[VERIFIED] Final retry attempt:** `assignment_students.latest_attempt_id` is updated when retry starts and again by atomic completion, so it is the correct final-attempt pointer.
