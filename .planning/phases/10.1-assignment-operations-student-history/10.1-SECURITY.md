## Corrected Threat: T-10.1-02 (Plan 01)

**Not an accepted risk -- a documentation correction.** The original Plan 01 threat-model wording said:

> "Review state must not overwrite student completion. The migration has no assignment-status trigger/update; review state lives only in receipts."

This is imprecise: Plan 01's own Task 1 action explicitly requires the owned atomic RPC to "atomically complete[] flagged assignment/attempt" for a `teacher_review` submission being accepted -- i.e., review state (acceptance) *does* legitimately finalize `teacher_review -> completed` through the RPC. The wording contradicted the plan's own acceptance criteria.

**Corrected invariant (from 10.1-CONTEXT.md / Plan 02):** Accepting an AI-flagged (`teacher_review`) submission MAY finalize `teacher_review -> completed` via the atomic, owned RPC. Undo/permanent-reopen actions clear only the review receipt and NEVER change already-completed homework status.

**Verified against current code:**
- (a) Atomic finalization to completed: `supabase/migrations/202607120002_review_any_attempt.sql:56-66` -- inside `mark_submission_reviewed`, the sole status-mutating branch is `if v_assignment_status = 'teacher_review' and v_attempt_status = 'teacher_review' then` ... updates `assignment_students.status = 'completed'` and `attempts.status = 'completed'` and inserts one `assignment_status_events` row with `reason_code = 'teacher_review_accepted'`. This whole function runs `security definer` inside one PL/pgSQL block with a `for update` row lock (lines 68-75) -- atomic by construction.
- (b) Undo/reopen never touches a completed row's status: `src/server/teacher/assignment-operations.ts:205-209` (`reopenSubmissionReview`) -- after the owned-attempt ownership check, the only mutation is `client.from("submission_review_receipts").update({ reviewed_at: null })...eq("teacher_id", ...).eq("attempt_id", ...)`. No call to `assignment_students` or `attempts` exists in this function. The UI's "Undo" toast and Plan 03/04's "Move back to Needs review" activity-overflow action both call this same `reopenSubmissionReview` service through `reopenSubmissionReviewAction` (`src/app/teacher/assignment-actions.ts:17`) -- there is exactly one reopen code path, and it is receipt-only.

The code matches the corrected invariant exactly as written; no code change was made or needed. This entry is recorded as **corrected/clarified**, not accepted or mitigated, because there was never an open vulnerability -- only imprecise threat-model prose from Plan 01 that a later plan's own documentation (10.1-CONTEXT.md, Plan 02) had already superseded.
