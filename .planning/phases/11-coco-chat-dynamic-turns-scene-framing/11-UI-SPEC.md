# Phase 11 — UI Design Contract

> Visual and interaction contract for Phase 11: scene premise framing (SCENE-01) and dynamic Coco Chat conversation mode (CHAT-01–06). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — confirmed no `components.json`, no `tailwind.config.*`, no `postcss.config.*` anywhere in the repo. Project deliberately uses plain inline `React.CSSProperties` objects (established since Phase 1, reconfirmed unchanged through Phase 9). |
| Preset | not applicable |
| Component library | none (hand-rolled). Shared student tokens live in `src/components/student/styles.ts`; teacher pages/components use colocated inline `CSSProperties` const blocks (e.g. `PronunciationDiagnosticPanel.tsx`, evidence page). Phase 11 follows this exactly — no new component library is introduced. |
| Icon library | none — no icon-font/icon-package dependency. Existing precedent uses hand-drawn inline SVG (`CocoSpeechAudio.tsx`'s `SpeakerIcon`, including an `animateTransform`-based spinner for the loading state) or plain text/Unicode glyphs (stars `★`/`☆`, arrows `←`). Phase 11's "Coco is thinking…" indicator must reuse this SVG-spinner pattern, not add a spinner library. |
| Font | `Inter, ui-sans-serif, system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif` |

This phase does **not** introduce a design system. It extends the existing hand-rolled token set with additive UI surfaces only: scene-premise text (student mission start + teacher evidence header), a conversation-mode toggle + required-turns control on the mission form, a "Coco is thinking…" indicator, a persisted Coco-line row per turn, a pattern-used badge, and a collapsed moderation-flag panel. All values below are reused from the existing codebase — no new hex, spacing, or font-size values are introduced except where explicitly flagged and justified.

**shadcn gate:** Not applicable. This is an established non-shadcn, non-Tailwind codebase (Next.js + hand-rolled inline styles), consistent across Phases 1–9. Introducing shadcn now would fragment the design system rather than unify it — out of scope for Phase 11, and explicitly a Phase 12 (UI Overhaul) concern if ever revisited.

## Spacing Scale

Declared values (multiples of 4 only) — extracted from existing `styles.ts` and evidence-page usage, not newly invented:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon/label micro-gaps (e.g. badge internal padding-top/bottom, tight label-to-value margin) |
| sm | 8px | Compact spacing — gap between the Coco-line row and turn heading, moderation-flag toggle padding |
| md | 12px | Card-internal gaps — diagnostic/flag panel padding, annotation grid gaps |
| lg | 16px | Default card padding, section spacing (`stepCardStyle`, buddy card, transition card) |
| xl | 24px | Page/panel padding, form field group gaps (`panelStyle`, `turnCardStyle`, `summaryStyle`) |
| 2xl | 32px | Page-level main content padding (evidence page `mainStyle`) |

Exceptions:
- Minimum interactive control height stays 44px (existing convention) — applies to the conversation-mode toggle, the required-turns stepper/select, and the moderation-flag disclosure button.
- Scene-premise card padding: 16px (matches `buddyCardStyle`/`resumeNoticeStyle` precedent for a lightweight, non-primary informational card) — not 24px, to keep it visually secondary to the turn/question card that follows it.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label / caption / badge | 14px | 600 | 1.4 |
| Heading (inline, per-card/section) | 20px | 600 | 1.25 |
| Display (page title) | 28px | 600 | 1.2 |

Exactly 2 weights used project-wide: 400 (body copy) and 600 (labels, headings, buttons, badges). No 500 or 700 weights appear anywhere in the existing codebase — Phase 11 additions must not introduce a third weight.

New elements this phase must fit into this scale:
- **Scene premise text** (student mission start, D-09): 16px/400/lh 1.5, matches `bodyStyle` — it is scene-setting narrative copy, not a heading. Rendered inside a lightweight card (see Layout Contracts), not as a bare paragraph, so it reads as a distinct "setting" moment before turn 1.
- **Scene premise line** (teacher evidence header, D-17): 14px/400/#4B5563 (matches existing `eyebrowStyle`/meta-text conventions) — smaller than the student-facing version because it sits in a dense header alongside the pattern chip, not as the primary reading content.
- **Target-pattern chip** (evidence header, D-14): 14px/600, pill-badge treatment (see Color section) — matches `statusBadgeBaseStyle` typography exactly.
- **Per-turn "pattern used ✓ / not yet" badge** (D-14): 14px/600, same badge scale as above, smaller footprint than the chip (inline with the turn heading, not a separate header element).
- **Coco-line row label** ("Coco said:", D-15): 14px/600/#4B5563, matches existing `labelStyle` pattern used above every transcript block.
- **Coco-line row text**: 16px/400/lh 1.5, matches `transcriptStyle` — visually identical treatment to the transcript blocks it sits above, since D-15 requires "no new layout."
- **"Coco is thinking…" indicator copy** (D-12): 16px/400/#4B5563, matches `bodyStyle` — sits inside the existing step-card scale, not a special "system status" typographic treatment.
- **Moderation-flag collapsed label** (D-16): 14px/600, matches the diagnostic-panel toggle pattern in `PronunciationDiagnosticPanel.tsx` exactly (same component family, same disclosure convention).
- **Conversation-mode toggle label + required-turns field label** (mission form): 14px/600, matches existing `labelStyle` in `MissionForm.tsx`/`styles.ts`.

**Accent (`#2563EB`) reserved for:** primary CTA buttons, primary nav/text links, the progress-bar fill, "start"/"continue" status badges, the `CocoSpeechAudio` speaker-button ready/playing state. **This phase adds one new accent usage:** the conversation-mode toggle's "on" state (matches the existing toggle/checked-control convention — see Component Notes) and the required-turns stepper's focus ring. No other new accent usage is introduced.

### Scene premise card (student + teacher)

Reuses the existing `buddyCardStyle` family exactly (no new color):

| Surface | Background | Border | Text |
|---------|-----------|--------|------|
| Student scene-premise card | `#EFF6FF` | `#BFDBFE` | `#111827` body text, `#1D4ED8` optional small "The scene:" eyebrow label |
| Teacher evidence-header premise line | none (plain text in header, not a card) | none | `#4B5563` (meta-text tier, per D-17 — sits next to the pattern chip, not boxed) |

Rationale: the student sees the premise as a distinct "buddy is setting the scene" moment (same visual family as the existing buddy-question card), while the teacher sees it as compact header metadata (D-17 explicitly says "short line in the header," not a new card).

### Target-pattern chip + per-turn pattern badge (D-14)

Reuses the existing 3-tier semantic badge family (Phase 4 `badgeDoneStyle`/`badgeRetryStyle`/`badgeClosedStyle` precedent — same convention as Phase 9's star-band tiers). No new hex values:

| Element | Background | Border | Text | Meaning |
|---------|-----------|--------|------|---------|
| Pattern chip (header, always shown, neutral) | `#EFF6FF` | `#BFDBFE` | `#1D4ED8` | Informational, not pass/fail — shows the mission's target pattern, always the same neutral-blue treatment regardless of any turn's outcome |
| Per-turn badge — "Pattern used ✓" | `#F0FDF4` | `#BBF7D0` | `#065F46` | Positive tier — reuses `evaluationSuccessStyle`/`badgeDoneStyle` family, driven by existing `turn.targetPatternResult === "Target pattern used"` |
| Per-turn badge — "Not yet" | `#F7F8FA` | `#E5E7EB` | `#6B7280` | Neutral tier (NOT red/error) — mirrors Phase 9's D-03 "1★ must not look like failure" rule; a student still practicing the pattern is not a failure state, so `#B91C1C`/error-red is explicitly forbidden here |

### Moderation-flag panel (D-16)

Reuses the Phase 9 collapsed-diagnostic-panel color pattern exactly (`PronunciationDiagnosticPanel.tsx`'s container/toggle/content styling) — same container (`#FFFFFF` bg, `#D1D5DB` border), same toggle button color (`#2563EB` text, transparent background). The flag icon/indicator itself (before expansion) uses the neutral-amber "minor issue" tier already established in Phase 9's word-level color mapping (`#FFFBEB` bg, `#FDE68A` border, `#92400E` text) — NOT the red/error family, because a moderation intervention is routine child-safety housekeeping (D-10/D-13's explicit "student never sees an error" framing), not a fault.

### Coco-line row (D-15)

No new color — renders with the exact same `labelStyle` (14px/600/#4B5563) + `transcriptStyle` (16px/400/#111827) pair used by every other transcript block on the evidence page (`TranscriptBlock` component). This is the point of D-15: purely additive, visually identical treatment to existing rows.

### "Coco is thinking…" indicator (D-12)

No new color — uses the existing `stepCardStyle` (white card, `#D1D5DB` border) with body text at `#4B5563` (matches `bodyStyle`) and the existing SVG-spinner pattern from `CocoSpeechAudio.tsx`'s loading state (`currentColor` stroke, inherits `#2563EB` from a wrapping accent-colored icon container — matches the speaker-button loading treatment already on screen elsewhere in the same flow).

## Interaction Contracts

### Student — Scene Premise (SCENE-01, D-09)

- Rendered once, above the first turn's question card, on mission start (both fresh start and resume — if `startingTurnIndex === 0`; not re-shown on subsequent turns).
- Static text, not voiced (D-09) — no `CocoSpeechAudio` wired to this card.
- No dismiss/collapse control — it simply scrolls past as the student progresses to turn 1's question card (matches the existing resume-notice pattern of being a transient, non-interactive lead-in).

### Student — Dynamic Turn / "Coco is thinking…" (CHAT-02, D-12)

- Appears in place of the next step card while the server round-trips (student-input moderation → conversation generation → Coco-output moderation → optional TTS fetch kickoff).
- Uses the existing `stepCardStyle` container with `aria-live="polite"` (matches the existing step-area `aria-live` wrapper already in `MissionFlowShell.tsx`) so screen readers announce the transition without interrupting.
- No cancel/skip action — the student waits; this mirrors the existing `isSubmittingVoice` disabled-controls pattern (submit controls disable during any in-flight request, no new pattern needed).
- No hard timeout copy is user-visible; if the request eventually resolves to the canned-fallback path (D-13), the student simply sees Coco's next line appear — the thinking indicator is replaced, never left hanging or showing an error.

### Student — Extending Past Required Turns (D-04)

- No "continue?" prompt, no new button. The existing turn-progression UI (question → feedback → repeat-if-needed → transition) simply continues to run past `required_turns` up to the hard cap, exactly as it already does for preset missions below their turn count — no new interaction pattern, this is the existing flow reused.

### Mission Form — Conversation Mode Toggle (D-06)

- Rendered as a labeled toggle switch (or checkbox styled as a toggle, matching whatever binary-control convention already exists in the codebase for boolean mission settings — if none exists, use a standard checkbox with the 44px-minimum touch target and accent-blue checked state, consistent with `primaryButtonStyle`'s accent usage).
- Default: off (unchecked) — matches D-06's "deliberate opt-in" requirement.
- When toggled on: the "Turns to complete this mission" field appears (range 3–8, default 5) and the existing per-turn `TurnEditor` authoring UI is either hidden or clearly marked optional/preview-only for chat-mode missions (RESEARCH.md Pitfall 1 — the `turns.length === requiredTurns` refine must not silently reject chat-mode drafts; the form must not present authoring UI that implies every turn needs hand-written content when Coco will generate them live).
- When toggled off: form behaves exactly as before Phase 11 — no visual change to existing preset-mission authoring.

### Mission Form — Scene Premise Field (D-07)

- Rendered as a labeled `<textarea>` (2–3 rows), positioned directly below the existing Target Pattern field (logical grouping — premise is generated from the pattern).
- Auto-populated when generated via the AI mission draft flow (existing `MissionDraftPanel.tsx` → `applyMissionDraft` pattern — extend the same apply function to also set premise state).
- For manually-created missions: a "Generate premise" button sits next to/below the field, calling a new generate-only action and filling the same field — teacher can still edit after generation, matching the existing draft-then-edit convention.
- Field is optional at the form-validation level for now (D-08 says premise applies mission-wide going forward, but the form must not hard-block save if premise generation fails — matches existing AI-degrades-gracefully philosophy).

### Teacher Evidence Page — Header Additions (D-14, D-17)

- Pattern chip and scene-premise line render inline in the existing header area, near the existing summary grid (`summaryStyle` section) — not a new separate section. Recommended placement: directly below the `h1` title, above the `summaryStyle` grid, as a single flex row: `[Target pattern chip] · Scene: {premise text, truncated to one line with ellipsis if long}`.
- Both are display-only, no interaction (no click/expand).
- If `conversation_mode` is false and `scene_premise` is null (pre-Phase-11 mission or preset mission created before this field existed): neither renders — header looks exactly as it does today.
- If `scene_premise` exists but `conversation_mode` is false (a preset mission that has a premise per SCENE-01 mission-wide framing): only the scene-premise line renders, no pattern-used badges appear on turn blocks (those are chat-mode-specific per D-14's "driven by AI evaluation" — preset missions already show pattern info via the existing `AnnotationGrid`'s "Target pattern result" row, so no duplicate badge is added there).

### Teacher Evidence Page — Per-Turn Additions (D-14, D-15, D-16)

- **Coco-line row**: renders as a new row at the top of each `TurnEvidenceSection` `<article>`, above the existing "Original answer" `TranscriptBlock`, using the identical `TranscriptBlock` component/pattern with label "Coco said:" — literally reuse the existing component, don't build a new one.
- **Pattern-used badge**: renders inline next to the `<h2>Turn {N}</h2>` heading (same row, right-aligned or immediately after), using the existing `statusBadgeBaseStyle` pill treatment — small, glanceable, not a full annotation-grid row (D-14 explicitly separates this from the inline-highlighting the transcript itself must avoid).
- **Moderation flag**: renders as a collapsed toggle button + hidden detail panel, positioned after the Coco-line row and before the `AnnotationGrid`, using the exact same disclosure component pattern as `PronunciationDiagnosticPanel.tsx` (button with `aria-expanded`, content `display: none/block` + `aria-hidden`, collapsed by default). Only renders when a moderation/fallback event occurred on that turn — otherwise omitted entirely (no "no issues" affirmative state needed, matches existing omit-when-empty convention seen in `AudioClipList`/`PronunciationDiagnosticList`).
- All three additions apply only to turns that have a `coco_line`/moderation event — preset-mode missions render identically to today (D-15's "preset and chat missions review identically" — the blocks are simply additive, not conditional on mission type at the component level, just on data presence).

## Component-Level Implementation Notes (for planner/executor)

These capture decisions the checker/executor need that don't fit the template's generic slots:

1. **Wind-down steering is server-side prompt construction, not client UI.** Per D-05/RESEARCH.md Pattern 2, the "wrap it up" nudge is injected into Coco's generation prompt (recommended trigger: turn 6+ of the fixed 8-turn hard cap, per RESEARCH.md Assumption A2/Open Question 2) and manifests as Coco's own generated line naturally winding down — there is no separate "wind-down" UI element, badge, or copy string to build. The client only ever renders whatever line Coco returns, exactly like every other turn.

2. **The hard 8-turn cap and the teacher's `required_turns` (3–8) are visually and functionally separate.** The existing `TurnProgressBar` component should continue to track against `required_turns` only (matches D-02's "existing progress bar and completion logic keep working off required_turns") — do not add a second progress indicator for the hard cap of 8. The student never sees "8" anywhere in the UI; the cap is a silent server ceiling (per RESEARCH.md Pitfall 4 — keep these two numbers architecturally and visually distinct).

3. **`StepCocoThinking` must be a real, separate step-card component** (not an inline conditional inside an existing step), because Phase 10's mascot work will later swap this indicator for an audio-driven idle/thinking mascot state (RESEARCH.md Don't-Hand-Roll table) — isolating it now avoids a refactor later.

4. **Reuse `TranscriptBlock` verbatim for the Coco-line row.** Do not create a new component/styling for this — the existing function in `src/app/teacher/evidence/[attemptId]/page.tsx` (label + transcript paragraph, `labelStyle` + `transcriptStyle`) already satisfies D-15's "labeled row, no new layout" requirement exactly. Only add a new component if the existing `TranscriptBlock` cannot be called with a `label="Coco said:"` prop from the turn-rendering loop without restructuring — check this during planning before assuming a new file is needed.

5. **`ModerationFlagPanel` should structurally mirror `PronunciationDiagnosticPanel.tsx`** (same `useState` expanded/collapsed pattern, same container/toggle/content style shapes) — copy its disclosure mechanics, swap in the four canned copy variants from the Copywriting Contract above based on the stored moderation-event type.

6. **Pattern-used badge visual weight must stay secondary to the turn heading.** It is a small pill, not a card, not a color-inverted banner — this is a glanceable annotation (D-14 spirit: "visually identifiable," not "visually dominant"). Do not let it compete with the `h2 Turn {N}` heading for attention.

7. **No new font, no new spacing unit, no new component library, and exactly one new-but-justified color decision** (none, in fact — this phase reuses 100% of existing hex values; unlike Phase 9's amber star-glyph exception, Phase 11 introduces zero new colors). The checker should treat any new hex/px value introduced during implementation as a deviation requiring justification.

8. **Scene-premise truncation on the evidence header** (single-line, ellipsis) is a CSS-only concern (`overflow: hidden; textOverflow: "ellipsis"; whiteSpace: "nowrap"` within a constrained flex-basis) — no "read more" interaction is in scope; the full premise is always visible to the student at mission start, and the header line is a teacher orientation cue, not the canonical record.
