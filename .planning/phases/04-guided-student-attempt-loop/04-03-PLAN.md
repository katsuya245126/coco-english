<objective>
Build the server-side mission-flow state machine and its server-action surface — the backend half of the turn slice. The service (`mission-flow.ts`) exposes start-or-resume, record-answer, record-repeat, and record-hint functions, all via the service-role client behind the unlock-cookie + ownership gate; a pure `completion.ts` helper computes "is this attempt complete?" and "what is the next unfinished turn?" without ever reading the `evaluation` field. The server actions (`actions.ts`) wrap each function with Zod input validation and the unlock gate. Completion (`started -> completed` + submitted_at stamping) and the full resume wiring land in plan 05; this plan delivers start/answer/repeat/hint and the completion helper that plan 05 will call.

Purpose: This is the deterministic, server-owned, audited core that the UI (plan 04) drives. Keeping the two swap points isolated — typed text fills `*_transcript`, placeholder eval fills `evaluation` — and keeping flow control off the `evaluation` field is the whole point of doing this as a clean backend slice (D-01/02/03/05, FLOW-02/04/05/07, AI-06).
Output: `mission-flow.ts` service, `completion.ts` pure helper, `actions.ts` server actions; `tests/server/mission-flow.test.ts` (from plan 01) goes GREEN for start/answer/repeat/hint.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> server action | Untrusted input (assignmentStudentId, turnOrder, transcripts, hintLevel) crosses here; identity comes only from the unlock cookie |
| server action -> service-role DB write | Every write must be scoped to the unlocked student; the service-role client bypasses RLS so app-level ownership is mandatory |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Elevation of Privilege | Student A writes to Student B's assignment | mitigate | Every service function loads `assignment_students` filtered by `id` AND `student_id = unlock.studentId` before any write (V4 Access Control) |
| T-04-07 | Tampering | Replay / double-submit of answer or repeat | mitigate | Upsert on `(attempt_id, turn_order)` unique key; repeat is an UPDATE of the existing row; status transition uses conditional UPDATE (Pitfall 2/3) |
| T-04-08 | Tampering | Duplicate attempts on re-entry corrupting attempt_count | mitigate | startOrResumeAttempt resumes the existing in_progress attempt and only inserts when status='assigned' (Pitfall 1, D-04) |
| T-04-09 | Information Disclosure | service-role key leak to browser | mitigate | service-role import is confined to `mission-flow.ts` (server-only, never `"use client"`); actions are `"use server"` |
| T-04-10 | Tampering | hint reveal corrupting completion / regressing highest_hint_level | mitigate | hint reveal is record-only and uses GREATEST; never touches status or repeat_accepted (D-08, Pitfall 7) |
| T-04-01 | Tampering | AI-06 erosion via a generation endpoint | mitigate | actions + service contain no AI import and no chat/buddy route; `ai-boundary.test.ts` re-runs against the new dirs (D-09) |
| T-04-11 | Input Validation | malformed action input | mitigate | Zod safeParse on every action input (V5 Input Validation) |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan (RESEARCH Package Legitimacy Audit: zero new packages) |

No `high` threat is left unmitigated.

**Schema push:** Not required. This plan writes only to pre-existing tables (`attempts`, `attempt_turns`, `assignment_students`, `assignment_status_events`) and adds no `supabase/migrations/*.sql` file.
