# Phase 2: Teacher Classroom Access - Context

**Gathered:** 2026-06-25
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase delivers teacher account access, teacher-owned class and roster management, and low-friction student entry into homework without student email/password accounts.

Teachers should be able to sign up, verify email, log in, see a class-list dashboard, create/manage classes, manage rosters, generate/reset student PINs, and share a stable class join code/QR link. Students should be able to reach a class through a QR/link or class code fallback, identify themselves, enter a 4-digit PIN, and land in a small student home shell that can show the no-homework state before mission assignment exists.

This phase should not build mission authoring, assignment creation, speaking attempts, audio recording, AI evaluation, or teacher review dashboards. Those belong to later phases.

</domain>

<decisions>
## Implementation Decisions

### Teacher Auth

- **D-01:** Use teacher email/password authentication with email verification required for the MVP.
- **D-02:** After verification, a teacher should land on an empty teacher dashboard with a clear Create class action.
- **D-03:** In Phase 2, the logged-in teacher dashboard should show the class list only: class name, roster count, join code/QR action, and archive/edit actions. Do not show future homework buckets yet.
- **D-04:** Keep teacher profile data minimal: store teacher display name only. Do not add academy/school metadata in Phase 2.

### Class And Roster Management

- **D-05:** Roster setup should support both bulk paste and one-by-one editing. Bulk paste should help teachers add a real class quickly, while individual editing handles corrections.
- **D-06:** Student 4-digit PINs should be auto-generated by default.
- **D-07:** Teachers must be able to change or reset a student's PIN later.
- **D-08:** Removing a student from a roster should archive the student, hiding them from the active roster while preserving history.
- **D-09:** Class join codes should be stable per class, with a teacher-initiated manual reset if needed.

### Student Join And Unlock Flow

- **D-10:** A QR/link should open the class directly, with manual class-code entry as fallback.
- **D-11:** Student identification should use typed name entry rather than roster name selection. Teachers can change roster names later if needed.
- **D-12:** After first access, the student device should remember the class.
- **D-13:** Remembering the class should not fully unlock homework. The student should still enter their PIN on each visit.
- **D-14:** After entering name and PIN in Phase 2, the student should land on a small student home shell showing class/name context and a no-homework state.

### Ownership And Access Boundaries

- **D-15:** Phase 2 should implement strict RLS-backed teacher ownership from the start. A teacher can only read/write their own classes, rosters, and linked future records.
- **D-16:** Wrong PIN behavior should show a generic error only in Phase 2. Do not reveal whether the class, student name, or PIN was the mismatched part.
- **D-17:** Do not issue a persistent student-auth account in Phase 2. The device may remember class context locally, but the student re-enters PIN each visit.
- **D-18:** Resetting a class join code or QR link should affect new entry only. Existing remembered devices can still reach the class; future access uses the new code/link.

### The Agent's Discretion

- The agent may choose exact route names, component boundaries, form validation helpers, and Supabase client wiring as long as the decisions above are preserved.
- The agent may choose a practical bulk-paste parser format, but it should support newline-separated names at minimum and surface duplicate/blank-name issues clearly.
- The agent may choose the exact join-code format, as long as codes are stable, unique, resettable, and suitable for elementary classroom sharing.
- The agent may decide how to hash and verify PINs, but plaintext PINs must not be stored.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `src/lib/supabase/server.ts` provides a server-side Supabase service client. Phase 2 likely needs authenticated user-aware Supabase client helpers in addition to this service-role client.
- `src/lib/db/types.ts` already includes partial generated/manual database types for `teacher_profiles`, `classes`, `students`, assignments, and status events. Phase 2 should update types as schema/policy usage expands.
- `src/components/foundation/FoundationSmokePanel.tsx` and `src/app/page.tsx` are only a foundation smoke UI. Phase 2 can replace the first screen with real teacher/student access entry points.

### Established Patterns

- The project is a Next.js App Router TypeScript app using Supabase and Zod.
- Phase 1 enabled RLS on the foundation tables but did not define teacher/session-specific policies.
- The schema already contains `teacher_profiles.auth_user_id`, `classes.join_code`, `students.pin_hash`, `students.archived_at`, and `classes.archived_at`, matching the Phase 2 surface.
- Phase 1 committed to class-scoped students rather than global student accounts.

### Integration Points

- `supabase/migrations/202606250001_foundation_schema.sql` is the current schema foundation. Phase 2 should add or adjust policies, constraints, indexes, helper functions, and any missing columns needed for teacher auth/class access.
- Teacher auth should connect Supabase Auth users to `teacher_profiles.auth_user_id`.
- Student access should use class code/QR and PIN verification without creating Supabase Auth user accounts for students.
- The no-homework student shell is a Phase 2 endpoint into later assignment and mission flows.

</code_context>

<specifics>
## Specific Ideas

- Teacher setup should feel like a small operational dashboard, not a marketing or feature-preview page.
- Teachers should be able to add a whole class quickly by pasting names, then correct individual entries.
- Students typing their name was preferred over choosing from a visible roster. This may reduce roster exposure on shared screens, but requires careful matching/error handling.
- Existing remembered devices should not be disrupted by a join-code reset; reset is mainly for future/new entry.

</specifics>
