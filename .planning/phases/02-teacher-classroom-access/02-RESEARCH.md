## User Constraints (from CONTEXT.md)

### Locked Decisions
## Implementation Decisions

### Teacher Auth

- **D-01:** Use teacher email/password authentication with email verification required for the MVP.
- **D-02:** After verification, a teacher should land on an empty teacher dashboard with a clear Create class action.
- **D-03:** In Phase 2, the logged-in teacher dashboard should show the class list only: class name, roster count, join code/QR action, and archive/edit actions. Do not show future homework buckets yet.
- **D-04:** Keep teacher profile data minimal: store teacher display name only. Do not add academy/school metadata in Phase 2.

### Class And Roster Management

- **D-05:** Roster setup should support both bulk paste and one-by-one editing. Bulk paste should help teachers add a real class quickly, while individual editing handles corrections.
- **D-06:** Student 4-digit PINs should be auto-generated by default.
- **D-07:** Teachers must be able to change or reset a student's PIN later.
- **D-08:** Removing a student from a roster should archive the student, hiding them from the active roster while preserving history.
- **D-09:** Class join codes should be stable per class, with a teacher-initiated manual reset if needed.

### Student Join And Unlock Flow

- **D-10:** A QR/link should open the class directly, with manual class-code entry as fallback.
- **D-11:** Student identification should use typed name entry rather than roster name selection. Teachers can change roster names later if needed.
- **D-12:** After first access, the student device should remember the class.
- **D-13:** Remembering the class should not fully unlock homework. The student should still enter their PIN on each visit.
- **D-14:** After entering name and PIN in Phase 2, the student should land on a small student home shell showing class/name context and a no-homework state.

### Ownership And Access Boundaries

- **D-15:** Phase 2 should implement strict RLS-backed teacher ownership from the start. A teacher can only read/write their own classes, rosters, and linked future records.
- **D-16:** Wrong PIN behavior should show a generic error only in Phase 2. Do not reveal whether the class, student name, or PIN was the mismatched part.
- **D-17:** Do not issue a persistent student-auth account in Phase 2. The device may remember class context locally, but the student re-enters PIN each visit.
- **D-18:** Resetting a class join code or QR link should affect new entry only. Existing remembered devices can still reach the class; future access uses the new code/link.

### the agent's Discretion
- The agent may choose exact route names, component boundaries, form validation helpers, and Supabase client wiring as long as the decisions above are preserved.
- The agent may choose a practical bulk-paste parser format, but it should support newline-separated names at minimum and surface duplicate/blank-name issues clearly.
- The agent may choose the exact join-code format, as long as codes are stable, unique, resettable, and suitable for elementary classroom sharing.
- The agent may decide how to hash and verify PINs, but plaintext PINs must not be stored.

### Deferred Ideas (OUT OF SCOPE)
None — discussion stayed within Phase 2 scope.

## Summary

Phase 2 should replace the Phase 1 smoke UI with a vertical classroom access slice: teacher email/password auth, teacher profile creation, class list, class creation/edit/archive, roster bulk paste/edit/archive, PIN reset, join-code/QR sharing, student class-code/link entry, typed roster-name lookup, 4-digit PIN unlock, and a no-homework student home shell. This directly maps to Phase 2 requirements and excludes mission authoring, assignment publishing, speaking attempts, audio, AI, and teacher review dashboards. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md] [VERIFIED: .planning/ROADMAP.md]

Use Supabase Auth for teachers and `@supabase/ssr` for cookie-backed Next.js App Router auth. Supabase's Next.js SSR docs specify separate browser/server clients and a proxy that refreshes Auth tokens, and its password docs cover `signUp`, email confirmation, `signInWithPassword`, and password reset flows. [CITED: https://supabase.com/docs/guides/auth/server-side/nextjs] [CITED: https://supabase.com/docs/guides/auth/passwords]

Student access must remain app-owned, not Supabase Auth. The server should resolve class code/link plus typed name plus PIN, verify a hash, return only a short-lived app session or Phase 2 shell state, and keep generic failure messages so attackers cannot enumerate classes, names, or PINs. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md] [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html]

**Primary recommendation:** implement one vertical slice over the existing Phase 1 schema: Supabase SSR teacher auth + RLS policies rooted in `teacher_profiles.auth_user_id = auth.uid()` + server-only roster/PIN services + typed-name student unlock routes + tests that prove cross-teacher isolation and generic student-auth failures. [VERIFIED: supabase/migrations/202606250001_foundation_schema.sql] [CITED: https://supabase.com/docs/guides/database/postgres/row-level-security]

## Architecture Patterns

### System Architecture Diagram

```text
Teacher browser
  -> /auth/signup, /auth/login, /auth/logout
  -> Supabase SSR browser client
  -> Next.js proxy refreshes session cookies
  -> Teacher server pages/actions call Supabase with user auth context
  -> RLS checks teacher_profiles.auth_user_id = auth.uid()
  -> classes / students / missions / assignments / attempts rows scoped by teacher ownership

Teacher class flow
  -> Create/edit/archive class
  -> Generate stable join_code
  -> Bulk paste roster or edit one student
  -> Server generates/resets 4-digit PIN
  -> Store only pin_hash, archived_at, display_name
  -> Show share link/QR and active roster

Student browser
  -> /join or /join/[joinCode]
  -> Class-code lookup returns class shell only
  -> Browser remembers class id/code locally
  -> Student types roster name + 4-digit PIN
  -> Server verifies generic tuple: class code + normalized name + PIN hash
     -> mismatch: generic error
     -> match: short student shell/session
  -> /student/home shows class/name context and no-homework/closed/expired states
```

### Pattern 1: Supabase SSR Teacher Auth

**What:** Add `@supabase/ssr` browser/server clients plus a Next.js proxy that refreshes sessions and use `auth.getClaims()` for server-side protection. [CITED: https://supabase.com/docs/guides/auth/server-side/nextjs]

**When to use:** Every teacher route, server action, and route handler that depends on the current teacher. [CITED: https://supabase.com/docs/guides/auth/server-side/nextjs]

**Example:**
```typescript
// Source: Supabase SSR Next.js docs, adapted to project naming.
// Use browser client in Client Components, server client in Server Components/actions.
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

export async function createSupabaseServerClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll: () => cookieStore.getAll(),
        setAll: (cookiesToSet) => {
          cookiesToSet.forEach(({ name, value, options }) => {
            cookieStore.set(name, value, options);
          });
        },
      },
    },
  );
}
```

### Pattern 2: RLS Rooted in Teacher Ownership

**What:** Bind profile rows to Supabase Auth users through `teacher_profiles.auth_user_id`, then scope class/roster/future records by direct or joined `teacher_id`. [VERIFIED: supabase/migrations/202606250001_foundation_schema.sql] [CITED: https://supabase.com/docs/guides/database/postgres/row-level-security]

**When to use:** All teacher reads/writes of `teacher_profiles`, `classes`, `students`, `missions`, `assignments`, `assignment_students`, `attempts`, `attempt_turns`, `audio_clips`, and status events. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]

**Example:**
```sql
-- Source: Supabase RLS docs; adapted for project ownership model.
create policy "teachers can read own classes"
on public.classes for select
to authenticated
using (
  exists (
    select 1
    from public.teacher_profiles p
    where p.id = classes.teacher_id
      and p.auth_user_id = (select auth.uid())
  )
);
```

### Pattern 3: Student Access as Server-Owned Unlock

**What:** Resolve class code/link and verify typed student name plus PIN on the server, then return a minimal student shell/session. Do not create Supabase Auth users for students. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]

**When to use:** Student join, unlock, no-homework, and later assignment list routes. [VERIFIED: .planning/ROADMAP.md]

**Example:**
```typescript
type StudentUnlockResult =
  | { ok: true; classId: string; studentId: string; displayName: string }
  | { ok: false; error: "generic_mismatch" | "class_closed" | "no_homework" };

// Keep the same public error for unknown code, unknown name, and wrong PIN.
export async function unlockStudent(input: {
  joinCode: string;
  typedName: string;
  pin: string;
}): Promise<StudentUnlockResult> {
  const normalizedName = normalizeRosterName(input.typedName);
  if (!/^\d{4}$/.test(input.pin)) {
    return { ok: false, error: "generic_mismatch" };
  }

  // Service implementation queries active class/student candidates, verifies
  // the stored hash server-side, and never returns which field mismatched.
  return verifyStudentAccessTuple({
    joinCode: input.joinCode,
    normalizedName,
    pin: input.pin,
  });
}
```

### Anti-Patterns to Avoid

- **Student Supabase Auth accounts:** This contradicts v1 scope and adds elementary learner account friction. [VERIFIED: .planning/REQUIREMENTS.md]
- **Plaintext PIN storage:** OWASP password-storage guidance rejects plaintext password storage; PINs are low entropy and still need protected storage. [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html]
- **Distinct wrong-code/wrong-name/wrong-PIN errors:** Generic failure is a locked Phase 2 decision and matches authentication error-message guidance. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md] [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html]
- **Client-owned ownership filtering:** Filtering by teacher in React is not authorization; enforce ownership in RLS and server services. [CITED: https://supabase.com/docs/guides/database/postgres/row-level-security]
- **Roster name picker exposed to students:** The newer Phase 2 context chooses typed name entry rather than visible roster selection. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Teacher password auth | Custom credential tables/password verification | Supabase Auth email/password | Supabase handles signup, confirmation, sessions, password reset, and signout. [CITED: https://supabase.com/docs/guides/auth/passwords] |
| SSR session refresh | Ad hoc cookie parsing | `@supabase/ssr` clients and proxy | Supabase documents cookie-aware clients and token refresh for Next.js SSR. [CITED: https://supabase.com/docs/guides/auth/server-side/nextjs] |
| Authorization by UI filtering | Hide rows after fetching all rows | Supabase RLS policies | RLS enforces row visibility at the database boundary. [CITED: https://supabase.com/docs/guides/database/postgres/row-level-security] |
| QR encoding | Manual QR drawing/encoding | `qrcode` after human/package verification | QR encoding has error correction and matrix rules; use a proven package after checkpoint. [ASSUMED] |
| Form validation duplication | Separate client/server validators | Zod schemas with React Hook Form resolver where useful | Shared schemas reduce drift between UI and server actions. [CITED: https://github.com/react-hook-form/resolvers] |
| PIN brute-force protection | Hash-only verification | Hash + pepper + throttling + generic errors | A 4-digit PIN has only 10,000 combinations, so online rate limiting is mandatory. [ASSUMED] [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html] |

**Key insight:** Supabase Auth solves teacher identity; it does not solve student identity because Phase 2 intentionally avoids student accounts. Student access is an app workflow that must be constrained by server checks, generic errors, rate limiting, and local-memory-only class recall. ## Common Pitfalls

### Pitfall 1: Treating the 4-Digit PIN Like a Strong Password

**What goes wrong:** The app stores a hash but allows unlimited online guesses against a 10,000-value space. [ASSUMED]  
**Why it happens:** Teams focus on avoiding plaintext and forget low-entropy online attack economics. [ASSUMED]  
**How to avoid:** Store only a salted/peppered hash, add per-class/student/IP throttling, keep generic errors, and test lockout/backoff behavior. [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html]  
**Warning signs:** No failed-attempt table/metadata, no server-only verify helper, and no E2E test for repeated wrong PINs. [ASSUMED]

### Pitfall 2: RLS Covers Classes but Not Linked Future Records

**What goes wrong:** Teacher A cannot read Teacher B's class row but can access linked assignments/attempts through missing join policies. [ASSUMED]  
**Why it happens:** Phase 1 enabled RLS but intentionally did not add session-specific policies yet. [VERIFIED: supabase/migrations/202606250001_foundation_schema.sql]  
**How to avoid:** Add policy tests for `classes`, `students`, `missions`, `assignments`, `assignment_students`, `attempts`, `attempt_turns`, `audio_clips`, and `assignment_status_events`. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]  
**Warning signs:** Policies exist only for `classes` and `students`, or tests prove only same-table ownership. [ASSUMED]

### Pitfall 3: Student Name Matching Leaks Roster Information

**What goes wrong:** The join flow tells a child whether the class code is valid, the name exists, or the PIN is wrong. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]  
**Why it happens:** UX tries to be helpful but creates enumeration paths. [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html]  
**How to avoid:** Use generic mismatch for all tuple failures and only show class context after safe class-link resolution. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]  
**Warning signs:** Error text says "student not found" or "PIN incorrect". [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]

### Pitfall 4: Join-Code Reset Breaks Existing Remembered Devices

**What goes wrong:** Resetting a class code logs out devices that already remembered the class, contrary to the locked decision. [VERIFIED: .planning/phases/02-teacher-classroom-access/02-CONTEXT.md]

// Source: Supabase SSR auth docs + project schema.
export async function requireTeacherProfile() {
  const supabase = await createSupabaseServerClient();
  const { data: claims, error } = await supabase.auth.getClaims();

  if (error || !claims.claims.sub) {
    redirect("/auth/login");
  }

  const { data: profile } = await supabase
    .from("teacher_profiles")
    .select("id, display_name")
    .eq("auth_user_id", claims.claims.sub)
    .single();

  if (!profile) {
    redirect("/auth/profile");
  }

  return profile;
}

### Join-Code Generator

```typescript
// Source: project discretion; keep code classroom-friendly and database-unique.
const JOIN_CODE_ALPHABET = "ABCDEFGHJKLMNPQRSTUVWXYZ23456789";

export function generateJoinCode(length = 6) {
  const bytes = crypto.getRandomValues(new Uint8Array(length));
  return Array.from(bytes, (byte) => JOIN_CODE_ALPHABET[byte % JOIN_CODE_ALPHABET.length]).join("");
}
```

### Roster Bulk Paste Parser

```typescript
// Source: Phase 2 context minimum parser requirement.
export function parseRosterPaste(input: string) {
  const names = input
    .split(/\r?\n/)
    .map((line) => line.trim())
    .filter(Boolean);

  const seen = new Set<string>();
  const duplicates: string[] = [];

  for (const name of names) {
    const key = normalizeRosterName(name);
    if (seen.has(key)) duplicates.push(name);
    seen.add(key);
  }

  return { names, duplicates };
}
```
