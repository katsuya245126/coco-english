<objective>
Deliver the teacher-access walking slice for Phase 2: a teacher can create an account (email/password with verification), log in, stay logged in across refresh, and log out, landing on a protected, empty class-list dashboard. This plan also lays the security spine the rest of the phase rides on: the `@supabase/ssr` client trio, the session-refresh middleware, and the RLS migration that roots all teacher-owned data in `teacher_profiles.auth_user_id = auth.uid()`.

This is a vertical slice, not a layer: after this plan a real teacher can sign up, verify, log in, see their (empty) dashboard, refresh without losing the session, and log out. The migration and RLS are folded in because the auth slice cannot function end-to-end without them.

Purpose: AUTH-01, AUTH-02, AUTH-03, AUTH-04 (D-01, D-02, D-04, D-15, D-16 spirit). Establishes the auth + RLS foundation reused by plans 02-04.
Output: SSR Supabase clients, session middleware, RLS migration (pushed to the database), teacher profile bootstrap/guard, signup/login/logout/profile-bootstrap routes and forms, protected dashboard shell, schema + e2e tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| teacher browser -> Next.js server actions/routes | Untrusted form input (email, password, display name) crosses here |
| Next.js server -> Supabase Auth | Credential verification and session issuance |
| Next.js server (user client) -> Postgres RLS | Row visibility enforced at the database boundary via auth.uid() |
| npm registry -> build | Dependency supply chain (@supabase/ssr, react-hook-form, @hookform/resolvers) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege / Information Disclosure | classes/students/assignments... reads | mitigate | RLS policies on all 11 teacher-owned tables rooted in teacher_profiles.auth_user_id = auth.uid(); schema test asserts policy presence; cross-teacher isolation verified in plan 04 |
| T-02-02 | Spoofing | teacher session cookies | mitigate | Use getClaims() (not getSession) for server protection per Supabase SSR guidance; session refresh in middleware; cookies are httpOnly via @supabase/ssr |
| T-02-03 | Information Disclosure | login/signup error messages | mitigate | Generic auth-failure copy; no "email already registered" / "user not found" distinction |
| T-02-04 | Elevation of Privilege | service-role key | mitigate | Service-role client confined to server-only modules (src/lib/supabase/server.ts); SSR user client uses anon key; acceptance criterion greps that no client component imports the service client |
| T-02-05 | Information Disclosure | per-user dashboard caching | mitigate | Follow Supabase SSR caching warning; do not statically cache authenticated /teacher pages |
| T-02-SC | Tampering | npm installs (@supabase/ssr, react-hook-form, @hookform/resolvers) | mitigate | All three packages verified OK in 02-RESEARCH Package Legitimacy Audit (official-doc-cited); qrcode is deferred to plan 02 behind a blocking human-verify checkpoint |
