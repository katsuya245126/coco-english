| Token | Value | Usage |

## Phase 2 Screen Contracts

### Teacher Auth

Use a centered, narrow form layout with a maximum width of 400px and no marketing hero. The form surface uses the Secondary color, 1px Border, 8px radius, and 24px padding. Signup captures display name, email, password, and confirm password. Login captures email and password. Email verification pending is a quiet status panel, not a blocking full-page illustration.

Primary action is full width on mobile and content width on desktop. Secondary links such as "Already have an account?" use Text secondary with underline on hover/focus. Password errors state what the user can fix; account enumeration errors stay generic.

### Teacher Dashboard

After verification, route teachers to a class-list dashboard. The first viewport contains a top app bar, page title `Classes`, a primary `Create class` button, and the class list or empty state. Do not show homework buckets, review tabs, mission counts, completion charts, or future assignment placeholders.

Class list rows are repeated items, not nested cards. Each row shows class name, roster count, join code, `Share join link`, `Show QR code`, edit action, archive action, and an overflow menu only if space requires it. Desktop uses a table-like list; mobile uses stacked rows with actions grouped at the bottom. Row height must stay stable when hover/focus states appear.

### Class Create/Edit

Class create/edit can be a dedicated page or modal, but it must keep the flow operational and compact. Required fields are class name and roster setup. Join code is generated by the system and displayed after class creation. Editing a class cannot expose mission or assignment settings in Phase 2.

Validation appears beneath the relevant field in 14px text. Disable save only while submitting; otherwise let users submit and show precise validation.

### Roster Editor

Roster setup has two modes: `Paste names` and `Add one`. Use tabs or a segmented control. `Paste names` accepts newline-separated names at minimum. After parsing, show a preview table with row number, display name, and issue status. Blank rows and duplicates are warnings/errors before save; do not silently discard them.

Active roster uses a dense table with columns: student name, PIN action, status, and row actions. PIN values may be shown only immediately after generation/reset, with copy action and clear "record this now" treatment. Archived students are hidden from the active roster by default.

### Join Code, QR, And Link Sharing

The share dialog shows class name, join code in large readable characters, link copy action, and QR code. Keep the QR code on a plain white surface with at least 16px quiet zone. Include a teacher-only `Reset join code` destructive action behind a secondary menu or dialog footer, not next to the primary copy/share controls.

Manual class-code fallback must be visible on the student entry page. Codes should be presented in grouped uppercase text if the implementation uses alphanumeric groups.

### Student Join And Unlock

Student pages are mobile-first with a maximum content width of 420px, 24px page padding, and 44px minimum controls. The flow is:

1. Class code entry or direct link opens class context.
2. Student types their name.
3. Student enters a 4-digit PIN.
4. Successful unlock lands on the student home shell.

Do not show a visible roster selector to students. Remembered class context may prefill or skip the class-code step, but PIN is still required on every visit. Wrong class, name, and PIN failures all use the same generic mismatch copy.

### Student Home Shell

The Phase 2 student home shell shows class name, student display name, and the no-homework state. It must not include mission cards, recording controls, buddy chat, progress rings, scores, leaderboards, or review feedback. Provide a small action to switch class or return to join entry.

## Interaction States

| Component | Required States |
|-----------|-----------------|
| Buttons | default, hover, focus-visible, disabled, loading |
| Inputs | default, focus-visible, invalid, disabled, readonly |
| Auth forms | idle, submitting, email verification pending, generic auth failure |
| Class list | loading, empty, populated, archive confirmation, action failure |
| Roster paste | empty, preview, duplicate/blank issue, submitting, saved |
| PIN actions | generated visible once, copied, reset confirmation, failed reset |
| Share dialog | link copied, QR visible, reset-code confirmation |
| Student unlock | class remembered, submitting, generic mismatch, no-homework success |

Focus rings use `#2563EB` at 2px with 2px offset. All dialogs close on Escape and include a visible close control. Toasts are allowed for non-destructive success; destructive confirmations must use dialogs or inline confirmations.

## Layout And Responsiveness

Use an app shell for teacher routes: top bar height 56px, content max width 1120px, horizontal padding 16px mobile, 24px tablet, 32px desktop. Avoid sidebars in Phase 2 because the only teacher destination is the class list and class detail.

Teacher desktop breakpoints:

| Range | Contract |
|-------|----------|
| `<640px` | Single-column, stacked class rows, full-width primary actions |
| `640px-1023px` | Single-column with wider forms and compact action groups |
| `>=1024px` | Table-like class list, class/roster editor can use two columns only when both columns remain readable |

Student routes are mobile-first at all sizes. On desktop, keep the student panel centered with max width 420px and no hero treatment.

---

## Accessibility Contract

All form controls require visible labels, not placeholder-only labels. Use `aria-live="polite"` for async success and status updates, and `role="alert"` for validation summaries or submit failures. Icon-only teacher actions must have accessible names and visible tooltips on hover/focus. Color cannot be the only indicator for duplicate names, invalid PIN, copied link, or destructive actions.

PIN input must support paste, numeric keyboard on mobile, and screen-reader label `4-digit PIN`. Error text must be associated with the relevant field using `aria-describedby`.

---

## Out Of Scope For This UI Contract

Do not design or implement mission authoring, assignment creation, speaking attempts, audio recording, AI evaluation, teacher review dashboards, parent accounts, school SSO, LMS sync, scoring, leaderboards, large character casts, or long-form chat in Phase 2.
